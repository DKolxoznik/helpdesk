# Спецификация сервиса заявок

## Проблема

Заявки на техническую поддержку приходят разными каналами. Сотрудники теряют обращения, не видят срок и вручную собирают отчёты. Нужен один сервер, который хранит заявку, контролирует её статус и считает сводку за период.

## Пользователи

- Оператор поддержки регистрирует заявку, уточняет описание, приоритет и срок, переводит её по статусам.
- Руководитель поддержки смотрит список, просрочку и сводку за период.

Аутентификация и роли в эту работу не входят: API открыт внутри учебной среды.

## Границы

Входит в объём:

- REST API заявок, категорий и сводки;
- PostgreSQL и миграции;
- история статусов;
- проверки бизнес-правил;
- контейнерный запуск и pipeline.

Не входит:

- экран для пользователя;
- несколько сервисов и Kubernetes;
- почта, чаты и вход по паролю.

## Пользовательские истории

### US-1. Зарегистрировать заявку

Оператор создаёт заявку, чтобы обращение не потерялось.

Критерии приёмки:

- без заголовка или категории API отвечает `400`, заявка не создаётся;
- приоритет только `LOW`, `MEDIUM` или `HIGH`;
- успешное создание отвечает `201`, статус заявки `NEW`, заполнены идентификатор и время создания;
- в истории есть первая запись с пустым предыдущим статусом и новым статусом `NEW`.

### US-2. Открыть заявку

Оператор открывает заявку по идентификатору.

Критерии приёмки:

- существующая заявка возвращается с категорией, сроком и историей;
- неизвестный идентификатор даёт `404`, тело ошибки в общем формате.

### US-3. Уточнить описание, приоритет и срок

Оператор меняет только эти три поля.

Критерии приёмки:

- у заявки в `NEW` или `IN_PROGRESS` изменения сохраняются;
- пустое описание очищает текст, флаг `clearDueAt` убирает срок;
- у `RESOLVED` и `CANCELLED` API отвечает `409`, описание, приоритет, срок, статус и история остаются прежними.

### US-4. Вести заявку по статусам

Разрешены переходы `NEW → IN_PROGRESS → RESOLVED`. Отмена разрешена из `NEW` и `IN_PROGRESS`.

Критерии приёмки:

- прямой переход `NEW → RESOLVED` даёт `409`, статус и история не меняются;
- при попытке перевести закрытую заявку в работу API возвращает `409`; статус и история заявки остаются неизменными;
- при `RESOLVED` и `CANCELLED` записывается время закрытия;
- повторно открыть такую заявку нельзя.

### US-5. Видеть историю

Оператор смотрит, как менялся статус.

Критерии приёмки:

- смена статуса и новая строка истории выполняются в одной транзакции;
- история в карточке заявки идёт по времени.

### US-6. Найти заявки

Оператор фильтрует список.

Критерии приёмки:

- можно отобрать по статусу, приоритету, категории, просрочке и фрагменту заголовка или описания;
- ответ содержит страницу: `content`, `page`, `size`, `totalElements`, `totalPages`;
- `page < 0` или `size` вне `1..100` даёт `400`.

### US-7. Выбрать категорию

Оператор берёт категорию из справочника.

Критерии приёмки:

- `GET /api/categories` возвращает код и название;
- неизвестная категория при создании заявки даёт `400`.

### US-8. Получить сводку

Руководитель запрашивает `GET /api/reports/summary?from=&to=`.

Критерии приёмки:

- в расчёт входят только заявки, созданные в полуоткрытом интервале `[from, to)`;
- ответ содержит число созданных, распределение по текущим статусам и приоритетам, число открытых просроченных и среднее время решения;
- среднее считается только по `RESOLVED` как разница времени закрытия и создания;
- если завершённых заявок нет, среднее равно `null`, а не нулю;
- при `from >= to` API отвечает `400`.

## Функциональные требования

| ID | Требование |
| --- | --- |
| FR-1 | Заявка хранит идентификатор, заголовок, описание, категорию, приоритет, статус, время создания, срок и время закрытия. |
| FR-2 | Начальный статус — `NEW`. |
| FR-3 | Приоритет: `LOW`, `MEDIUM`, `HIGH`. |
| FR-4 | Переходы: `NEW → IN_PROGRESS → RESOLVED`; отмена из `NEW` и `IN_PROGRESS`. |
| FR-5 | `RESOLVED` и `CANCELLED` нельзя редактировать и открывать заново. |
| FR-6 | Смена статуса и запись истории атомарны. |
| FR-7 | Заявка просрочена, если срок задан, `dueAt <= текущего времени` и статус `NEW` или `IN_PROGRESS`. В момент наступления срока она уже просрочена. |
| FR-8 | Список поддерживает фильтры и пагинацию. |
| FR-9 | Сводка строится по одной выборке заявок, созданных в `[from, to)`. |
| FR-10 | Нет заявки — `404`. Ошибка проверки полей — `400`. Запрещённый переход или правка закрытой заявки — `409`. |

## Нефункциональные требования

| ID | Требование |
| --- | --- |
| NFR-1 | Запуск воспроизводится через `docker compose` и зафиксированные версии инструментов. |
| NFR-2 | Данные PostgreSQL лежат в постоянном томе и переживают перезапуск контейнеров. |
| NFR-3 | Ошибки API имеют один формат: время, код, краткий статус, сообщение, путь и список полей. |
| NFR-4 | В репозитории нет паролей и токенов. Пример настроек — `.env.example`. |
| NFR-5 | Время в правилах и тестах берётся из `Clock`, поэтому результат не зависит от даты запуска. |
| NFR-6 | Миграции применяются при старте. Новые миграции только добавляют объекты и не ломают предыдущую версию приложения. |
| NFR-7 | Приложение пишет логи в stdout и отдаёт readiness-проверку с состоянием базы. |
